## 1. DB 확장성 리뷰 — 최저가 차트 / 검색이 가능한 구조인가

결론부터: 파서층(커뮤니티별 원문 보존)은 설계 목적대로 잘 만들어져 있고, 중앙 스키마(`types.ts`의 Deal)도 핵심 필드는 갖췄다. 다만 **DB화 전에 중앙 레이어에서 정책 결정이 필요한 gap 5개**가 있다. 파서 raw → 중앙 Deal 2단 구조라 파서를 건드리지 않고 추가할 수 있는 것들이다.

### 1.1 최저가 선형 차트 관점

차트의 필요 조건은 세 가지다: (a) "같은 상품"임을 알아보는 상품 식별 키, (b) 시간축, (c) 통화 통일.

| 필요 요소 | 현재 스키마 | 상태 |
|---|---|---|
| 상품 식별 키 | `purchase.itemId`, `product.productId` | 부분 충족 |
| 시간축 (게시 시각) | `sourcePost.postedAt` | 충족 (이번 점검에서 fmkorea도 채움) |
| 시간축 (수집 시각) | `collectedAt` | 충족 |
| 가격 스냅샷 | `price.dealPrice` | 충족 — append-only 저장 시 그대로 시계열 |
| 통화 통일 | `price.currency`, `price.estimatedKrw` | 필드 존재, 환율 로직 미구현 |
| 최저가 비교 블록 | `priceHistory.*` | 전부 null — 의도된 상태 |

**itemId 커버리지가 차트의 병목이다.** 현재 추출 패턴은 두 개뿐이다:

- AliExpress: `/item/(\d+).html` → item id
- Coupang: `/vp/products/(\d+)` → product id

오늘 라이브 샘플의 실측: fmkorea 8건 중 쿠팡 3건, 오늘의집 2건, 알리 1건, 네이버 1건, 11번가 1건, 롯데온 1건. 쿠팡/알리는 itemId가 잡히지만 오늘의집(`store.ohou.se/goods/2010432` — `goods/(\d+)` 패턴으로 잡을 수 있음), 11번가, 네이버, 롯데온은 아직 패턴이 없다. URL 패턴 사전(스토어별 1줄 정규식)을 늘리는 것만으로 커버리지가 크게 올라간다.

패턴으로도 식별 안 되는 상품(단축링크, 앱 전용 딜, 모음글 내 상품)은 결국 상품명 정규화(`normalizedName`, 현재 보류 항목)가 있어야 조인이 된다. 즉 최저가 차트는 "1단계: URL id 기반(정확, 커버리지 제한) → 2단계: 상품명 정규화(커버리지 확장)" 순서로 가는 게 현실적이다.

`priceHistory` 블록을 파서가 비워두는 것은 올바른 설계다 — 최저가는 DB에 쌓인 스냅샷에서 조회 시점에 계산해야지, 수집 시점에 판단할 게 아니다.

### 1.2 검색(키워드/메타태그) 관점

키워드 검색 대상 필드는 이미 충분하다: `title`, `product.name`, `product.store`, `product.category`, `discount.types`, `discount.codes`. 텍스트 검색 자체는 막히는 게 없다.

문제는 **필터링용 정규화**다:

1. **스토어 정규화 부재.** 오늘 샘플에서만 "알리"(표기는 알리인데 도메인은 aliexpress.com), "오늘의집", "쿠팡"이 혼재한다. 같은 스토어를 묶으려면 에이리어스 테이블이 필요하다. 좋은 소식: fmkorea 통합공지에 "포텐 우대 쇼핑몰" 도메인 48개 목록(coupang.com, gmarket.co.kr, aliexpress.com, 11st.co.kr, lotteon.com, ...)이 공개돼 있어서 그대로 시드 테이블로 쓸 수 있다. raw 값 보존용 필드(예: `storeRaw`)를 같이 두는 것을 권한다.
2. **카테고리 정규화 부재.** fmkorea 13개(먹거리/SW게임/가전제품/...), ppomppu 9개(기타/패션뷰티/식품건강/...)가 그대로 들어온다. 통합 택소노미 + 매핑 테이블이 없으면 "가전만 보기" 같은 필터가 커뮤니티별로 따로 논다.
3. **tags 필드 자체가 없다.** 커뮤니티 용어(네멤무료, 티멤, 재입고, 품절, 찐막...)를 저장할 곳이 현재 스키마엔 없다. `tags: string[]` 추가 + 사전 기반 추출을 권한다(4절 참고).

### 1.3 DB화 전 결정할 것들 (우선순위)

1. **상품 키 정책**: `(community, store, itemId)`를 기본 키로 하고, itemId 없으면 상품명 정규화 대기열로. 스토어별 URL id 패턴 사전 확장이 먼저.
2. **append-only 스냅샷 정책**: 같은 딜이 다시 수집돼도 갱신하지 않고 새 행으로 쌓아야 차트가 된다. `dealId`는 게시글 단위이므로 `(productKey, collectedAt)`이 실질적 시계열 키.
3. **스토어/카테고리 에이리어스 테이블** + raw 보존 필드.
4. **tags 필드 추가**와 사전 1차분(배송/멤버십/딜 상태 용어).
5. **환율 스냅샷**: USD 딜(알리)의 원화 차트를 위해 수집 시점 환율을 `estimatedKrw`와 함께 저장.

### 1.4 참고: 권장 테이블 형태

```
posts    — 커뮤니티 원문 아카이브 (parser-native 출력 그대로, 불변)
deals    — 상품 단위 스냅샷 (append-only; price/stats/collectedAt)
products — 상품 마스터 (productKey, normalizedName, itemId, storeId)
stores   — 스토어 마스터 + 도메인/에이리어스
categories — 통합 카테고리 + 커뮤니티별 매핑
tags     — 딜-태그 연결
```

posts를 원문 그대로 남기는 지금의 2단 구조가 이 설계와 정확히 맞아떨어진다. 재처리(재파싱)가 필요해져도 원문이 있으면 파서만 고치면 되지 재수집이 필요 없다.

## 2. fmkorea 핫딜 게시판 구조 조사 (라이브)

### 2.1 기본 구조

- XE 엔진 + sketchbook5 스킨, 게시판 `mid=hotdeal`
- 목록 뷰 2종: webzine(이미지, 기본) / list(텍스트) — `listStyle=list|webzine`
- 카테고리 13개(숫자 srl): 먹거리 1196844726, SW/게임 1196844901, PC제품 1254381811, 가전제품 1196845148, 생활용품 1254371833, 의류 1196845284, 세일정보 1268060631, 화장품 1200453691, 모바일/상품권 1200454594, 패키지/이용권 1254448931, 기타 1196367767, 해외핫딜 1200503163, 공지 1200490854
- 목록 URL 파라미터: `page=N`, `category=<srl>`, `sort_index=voted_count|pop`, `order_type=desc`, `search_target=title`, `search_keyword=<urlencoded>`
- 게시글 URL: `https://www.fmkorea.com/<document_srl>` (srl은 단조 증가 → 증분 수집의 중단점으로 사용 가능)

### 2.2 목록 페이지가 이미 주는 것 — 크롤러 효율의 핵심

텍스트 목록 1행(서버 렌더링): **카테고리 | 제목 | 글쓴이 | 날짜(MM.DD 또는 HH:MM) | 조회 | 추천** (+ 제목 옆 댓글 수).
webzine 목록은 여기에 `hotdeal_info` 블록으로 **쇼핑몰/가격/배송**까지 구조화해서 준다.

즉 상세 페이지를 열지 않고도 "이 딜을 수집할 가치가 있는지" 판단할 재료가 전부 있다. 권장 수집 전략:

1. 목록 페이지 순회(요청 1회당 20건 정보) → 추천 수/등록 시각/스토어로 필터
2. 통과한 글만 상세 fetch
3. 마지막으로 수집한 document_srl을 만나면 중단(증분 수집)

상세 페이지는 100~170KB, 목록은 18KB 수준이라 이 전략은 트래픽과 차단 리스크를 동시에 줄인다.

제목 규칙은 `[쇼핑몰] 상품명 (옵션) (가격) (배송)` — 예: `[알리] ALLDOCUBE iPlay80 mini Pro LTE 태블릿 (카드$85.92) (무료)`. 게시글 작성 폼(hotdeal_table: 링크/쇼핑몰/상품명/가격/배송)에서 자동 조합되는 것으로 보이며, 오늘 표본 8건 전부 폼이 채워져 있었다.

### 2.3 WAF / 안티봇 (실측)

이번 점검에서 실제로 차단됐다. 교훈:

- 1초 간격 연속 20건 상세 요청 → 12건째부터 "에펨코리아 보안 시스템" 챌린지 페이지 → 직후 **429 자동 차단**(차단 종류: D C, 일시적 IP 차단)
- 챌린지 메커니즘: `lite_year` 쿠키(7일) 설정 + WASM 모듈(`/mc/mc.php`의 `fm5()`) 실행 + `?ddosCheckOnly=1` 리다이렉트. **쿠키만 복제해서는 통과 불가**(429 확인) — WASM 단계의 서버 검증이 있는 것으로 추정
- 단일 요청(수동 curl)은 모두 200 통과 → 임계값은 "짧은 시간 내 연속 요청"

향후 크롤러 필수 요건: 요청 간 5~10초 이상 스로틀링, 목록 우선 전략으로 상세 요청 최소화, 세션(쿠키) 유지, 챌린지 페이지 감지 시 백오프. 수집 빈도 목표(예: 5~10분 간격 목록 1회) 기준으로 하루 상세 요청은 수십 건 이내로 설계해야 안전하다.

### 2.4 통합공지에서 확인한 규칙

- **제휴 링크 자동 변환**: 우대 쇼핑몰 도메인 링크는 fmkorea가 제휴 링크로 자동 변환. 우대 도메인 48개 목록 공개(coupang.com, gmarket.co.kr, aliexpress.com, 11st.co.kr, lotteon.com, ssg.com, amazon.com, iherb.com, agoda.com, ...). 제휴 시 쇼핑몰 행에 `[포텐 터짐 우대 쇼핑몰, 제휴 링크]` 표기 — 파서가 이미 감지한다.
- 단축 URL 금지(그래서 본문 링크가 대부분 완전한 URL — resolver 입장에서 유리)
- 라이브 방송 딜, 추천인/공동구매 링크 금지 → 이 게시판에는 해당 유형이 거의 안 나온다
- 세일정보 카테고리, 모음글 일부는 폼 없이 자유 형식일 수 있음(3.3절 리스크)

### 2.5 발견한 보너스 데이터 소스: `relevant_hotdeals` 위젯

상세 페이지 하단(article 밖)에 "유사한 최근 6개월 핫딜들" 위젯이 있다. 각 항목: 제목, **가격**, **본문 상품 대비 비쌈/저렴 차이**, **등록일(YYYY-MM-DD)**, 원문 링크. 예: 잘풀리는집 화장지 딜 페이지에 같은 상품 과거 딜 40건이 날짜+가격과 함께 붙어 있다.

지금은 의도적으로 파싱하지 않는다(article 밖 + 인계서 범위 외). 하지만 향후 최저가 차트의 시드 데이터로 쓸 수 있는, **추가 수집 비용 0**(이미 받는 HTML 안에 있음)의 데이터 소스다. 단 "유사 상품명" 기반이라 상품 매칭(정규화) 문제가 함께 따라온다.

### 3.1 고친 버그 2건 (라이브에서 발견)

**① 다중 상품 오분리 (치명적).** 알리 태블릿 딜에서 본문의 "코인 할인 받는 방법" 번호 목록(`1. 장바구니담기 / 2. 홈 → 코인 → ...`)을 상품 2개로 분리하고, 그중 하나의 이름("장바구니담기")이 hotdeal table의 진짜 상품명("ALLDOCUBE iPlay80 mini Pro LTE 태블릿")을 덮어쓰고 있었다.
수정: 번호 섹션이 **가격 또는 URL을 동반할 때만** 상품으로 인정. 이름만 있는 섹션은 상품 증거 부족으로 판정(인계서 원칙 "확신 못 하면 null/분리 안 함"과 동일 방향).
회귀 방지: 라이브 원문을 `tests/fixtures/fmkorea-10256348563.html`로 고정하고, 스키마 검증 외에 값 수준 assertion(상품 1개 유지, table 상품명 보존, 코드 2개 추출)을 추가했다.

**② 할인 코드 누락.** 실제 글은 "코드 ALPK07", "스토어쿠폰 CUBET830" 형식을 쓰는데 파서는 "할인코드/쿠폰코드" 접두만 잡고 있었다. 대문자 영숫자 토큰 제한(한국어 문장 오탐 방지)을 유지하며 `코드`/`쿠폰` 마커 패턴 추가. 수정 후 두 코드 모두 추출 확인.

### 3.2 이번 점검에서 같이 반영한 항목

- fmkorea `postedAt` 추출 추가(`.rd_hd .date.m_no`의 `YYYY.MM.DD HH:MM` → ISO +09:00). 기존 fixture 3종 + 라이브 전부 정상 추출. ppomppu와 비대칭이 해소됐고, 시계열 DB의 게시 시각 축이 양쪽 커뮤니티에서 확보됐다.
- (직전 세션) 스키마 `product.name` nullable 허용 — "추출 실패 시 지어내지 않음" 원칙과 스키마가 어긋나던 부분.

### 3.3 리스크 처리 정책 (2026-08-26 결정)

**① 폼 미입력 글 → 수집 스킵.** hotdeal_table 폼에 맞지 않아 필드 구분이 어려운 글은 이 단계에서 수집하지 않는다. 근거: 유용한 딜이 아니거나 프로모션 공유일 가능성이 높음. 판별 지점은 크롤러 단계(상세 파싱 결과 `products: []`이면 스킵). 목록 webzine의 `hotdeal_info` 유무로 상세 진입 전에 거르는 최적화는 가능 여부 미검증 — 크롤러 구현 시 확인. 스킵하더라도 왜 스킵했는지는 카운트로 남겨서(제목/카테고리 수준) 폼 미입력 비율을 나중에 측정할 수 있게 한다.

**② 성인/연령 제한·삭제 글 → 스킵.** 참고로 핫딜 게시판 자체 규칙이 성인용품 업로드 금지(게시판이 성인인증 게시판이 아님)라 연령 제한 콘텐츠는 사실상 유입되지 않는다. 실제로 만나게 될 케이스는 삭제된 글(에러/알림 페이지)과 WAF 챌린지 페이지 — 둘 다 크롤러에서 감지해 스킵하고, **챌린지 페이지 HTML은 절대 게시글로 저장하지 않도록** 주의.

**③ 본문 내 모음글 링크 → 별도 필드로 수집, 프론트 미반영.** 게시판 규칙상 금지지만 실제로 존재하므로, 상품 링크와 분리해 수집만 해두고 추후 모음/프로모션 페이지 기능의 재료로 쓴다.
구현 완료: `FmkoreaDeal.sourceMeta.internalLinks` — 본문(article 범위)에서 발견된 fmkorea 내부 게시글 링크를 `{rawUrl, url(정규화), text(해당 줄 원문)}`로 수집. 자기 자신 링크 제외, 정규화 URL 기준 중복 제거. 자동 삽입되는 `relevant_hotdeals` 위젯 링크는 article 밖에 있어 섞이지 않음(의도된 동작). ppomppu는 이미 `sourceMeta.links`에 전체 링크를 보존하므로 별도 작업 불필요. 중앙 Deal 매핑/프론트 노출은 기능 추가 시점에.

## 4. 커뮤니티 용어 처리 — 정직한 평가

**fmkorea는 구조적으로 안전하다.** 핵심 데이터(상품명/가격/스토어/배송)가 작성 폼 강제 + 제목 자동 조합에서 나오기 때문에 본문이 아무리 은어로 쓰여도 딜의 뼈데이터는 흔들리지 않는다. 본문의 모호함은 할인 정보(description/codes)에만 영향을 주고, 그 부분은 증거가 명확한 것(코드 토큰, 쿠폰 키워드)만 추출하는 현재 접근이 맞다.

**ppomppu가 진짜 어려운 쪽**이다(폼 강제 없음). 지난 라운드의 체감가/혜택가 변형 처리, 0원 라인 제외, 마커 우선순위 가격 선택이 모두 이 문제에 대한 대비였다.

오늘 실제로 마주친 용어들: "찐찐막"(=진짜 마지막, 딜 종료 임박), "카할"(카드할인), "재입고", "모음"(모음글), "네멤무료"(네이버멤버십 무료배송), "티멤"(T멤버십).

권장 로드맵(인계서의 보류 범위와 양립):

1. **1단계 — 사전 기반 태그**(저위험, 규칙 기반): 배송/멤버십 약어(네멤무료→네이버멤버십+무료배송), 딜 상태(품절/종료/재입고), 스토어 약어(알리→알리익스프레스). `tags` 필드 추가가 선행 조건.
2. **2단계 — AI 상품명 정규화**(고위험/고수익): 크로스 게시글 상품 매칭과 최저가 차트 커버리지의 최종 해결책. 현재 설계상 `normalizedName` 자리 비워둠.

1단계는 파서가 아니라 중앙 레이어(normalize 또는 DB 적재 시점)에서 하는 것이 맞다 — 파서는 원문을 있는 그대로 남기는 역할을 유지해야 재처리 비용이 안 생긴다.

## 9. 테스트 크롤링 실측 (2026-08-26) — 3곳 9/9 상세 수집 성공

`tests/live-crawl-test.ts`로 목록→상세→파서 전 구간 실수집. 스로틀: ppomppu/ruliweb 3초, fmkorea 7초. 실행 중 WAF 챌린지 발생 없음(fmkorea는 과거 1초 간격 시 429 전례 있어 보수적 간격 유지).

**ppomppu — 크롤링이 찾아낸 파서 결함 2건, 수정 완료**

1. 제목 댓글수 오염: 크롤러 수신 HTML의 `#topTitle h1` 안에 `<span id="comment">N</span>`이 들어 있어 `text()` 추출 시 제목 끝에 댓글수가 달라붙음("…냉장 1kg4"). 브라우저 캡처 fixture에는 없어 기존 테스트로 잡히지 않던 변형 — extractTitle이 클론에서 스팬을 제거하도록 수정.
2. 단일 상품 글 name: null: 기존 설계는 "제목에 마케팅 문구가 섞여 상품명 단정 불가"라며 null로 두고 Product Resolver 단계로 미뤘으나, 실수집 딜 대부분이 단일 상품 글이라 표시용 이름 공백이 큼. ruliweb과 같은 접근으로 제목 폴백(nameFromTitle) 추가 — 첫 [...] 태그 제거 + 꼬리 가격/배송 괄호 제거(토큰 판정: "(6,400원/무료)" 제거, "(16인치)" 보존) + 괄호 없는 꼬리 가격("231만원대~") 제거. 지어내는 값이 아니라 게시글 자신의 제목을 정리한 것이라 원본 유지 원칙과 충돌 없음. 상품 매칭은 URL 기반 product key 담당.

목록 필터도 실측에서 강화: `view.php?id=regulation` 등 공지/규정 글 링크가 pmarket 목록에서 같이 잡혀 `[?&]id=pmarket(&|$)` 필터 추가.

**fmkorea** — 상세 3건: 딜 2건 파서 통과(항공권 딜 포함), 1건은 공지성 규정 글이라 hotdeal_table 폼 없음 → products: [] 스킵(폼 게이트 정상 동작 실증). 목록에 고정 공지가 섞이므로 향후 목록 필터에서 공지 제외 최적화 여지 있음(현재는 파서 게이트가 방어).

**ruliweb** — 상세 3건 전부 파서 통과. 관찰: 에픽게임즈 무료 게임 딜("(무료)")은 가격 0이 아닌 price null로 남음 — ruliweb의 "(무료)"는 배송비 무료 규약이라 가격 0 판정은 보류(무료 아이템 처리는 DB 단계에서 재검토). PSN 세일 모음글은 가격 null 허용 케이스로 정상.

**회귀 고정**: 라이브 스냅샷 3종(303716/303718/303717-live)을 fixtures에 추가, ppomppu 값 수준 assertion 20종 신설 — 제목 폴백, 댓글수 스팬 제거, 다중 상품 분리, 옵션 나열, price null 안전 실패, 확정 종료 서술(조건부 서술 공존) 포함. 전체 스키마 테스트·status 가드·tsc·build PASS.

**quasarzone/arca 수집 여부**: 양쪽 모두 Cloudflare 챌린지로 헤드리스 수집 불가라는 실측 재확인. 파서는 fixture 검증 상태로 유지. 결정 대기.

## 10. quasarzone/arca 수집 경로 조사 (2026-08-26) — "크롤링 외 방법" 결론: Chrome 지문 HTTP 크롤링

**계기**: 수집 여부 결정 질문에 사용자가 dajupma.com(커뮤니티 특가 집계 사이트)이 아카라이브 글을 가져오는 방식을 조사해 달라고 요청.

**dajupma.com 분석**

- Next/React 아님 — 서버 렌더 SPA 셸 + `GET /api/deals?limit=1200` JSON API. 응답에 자체 크롤 로그(`lastCrawl`)가 그대로 노출됨.
- 로그 실측(2026-08-26 07:22 UTC): 아카라이브 `ok: true, count: 26`, 루리웹 85, 클리앙 88, 더쿠 딜방 23 등 — 서버 측 크롤러로 15개 커뮤니티를 주기 수집. **퀘이사존은 그쪽도 `HTTP 403` 실패 중**. fmkorea는 별도 "external crawl" 경로(20건 수신) 운영.
- 공개 RSS/API/미러 같은 우회 데이터 소스는 없음 — 결국 각 사이트를 직접 수집하는 구조.

**핵심 발견: Cloudflare 챌린지가 TLS 지문 기반**

- arca.live RSS(`arca.live/rss/b/hotdeal`)도 "Just a moment" 403 → 일반 HTTP 클라이언트의 지문이 차단 원인.
- `curl_cffi`(Chrome TLS/HTTP2 지문 모방)로 실측: arca.live 목록·상세, quasarzone 목록·상세 **모두 챌린지 없이 200**. IP 평판 문제가 아님(데이터센터 호스팅 Render의 dajupma 서버도 통과).
- 헤드리스 브라우저가 막혔던 이유도 동일한 지문 판정일 가능성이 높음 — 브라우저 자동화 없이 요청 레벨 크롤러로 충분.

**파서 호환 실측**

- 크롤러 수신 arca 상세(181084175) 파싱: 제목/상태(LIVE)/KST 변환/상품(18,900원·지마켓·gmarket URL 언래핑) 전부 정상. 단 stats 라벨이 ko Accept-Language 기준 한국어("조회수/추천/댓글")로 와서 기존 영어 전용 매칭이 null → **영어+한국어 라벨 모두 처리하도록 arca 파서 수정**, 해당 페이지를 fixture로 승격 + assertion 3종 고정.
- 크롤러 수신 quasarzone 상세(1981977) 파싱: 진행중 라벨·무료 게임(0원)·epicgames URL·stats 전부 정상(무수정).

**결론**: "크롤링 외 방법"은 존재하지 않지만(공개 API/RSS 없음), 헤드리스/브라우저 없이 Chrome 지문 HTTP 크롤러로 두 커뮤니티 모두 수집 가능. 수집 시 Chrome 지문 모방 클라이언트 + 보수적 스로틀 필요. 수집 여부 최종 결정만 남음.
